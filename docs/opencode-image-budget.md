# OpenCode image budget

`kdn.image-budget` keeps every OpenCode request inside a gateway's image cap. It is a server plugin,
generated by the `kdn.opencode` den aspect from
[`modules/den/aspects/opencode/kdn-image-budget.ts`](../modules/den/aspects/opencode/kdn-image-budget.ts).
The task that produced it, with the full evidence, is
[docs/tasks/2026-11/opencode-image-budget/](tasks/2026-11/opencode-image-budget/definition.md).

## Why it exists

A gateway caps how many images one request may carry: **30** for requesty and the OpenCode gateway,
**50** for Azure. OpenCode caps the *bytes* of an image (`media.image.max_base64_bytes`, 5 MiB by
default) and never the *count*, and the cap is not in the model metadata, so no setting expresses
it.

A session that collects screenshots — a NanoKVM loop, a repeated `read` of a PNG, a multi-page PDF —
reaches the cap. From that moment every request fails:

```
AI.Error: Too many images in request: 69 > 30
```

The failure is classified `provider.invalid-request`, **not** context overflow, so `compaction.auto`
never triggers. `/compact` fails the same way, because a compaction request carries the same images.
The session is bricked, and only a new session or a manual database edit recovers it.

## What the plugin does

It prunes the **outgoing request**, never the transcript:

1. It keeps the newest images inside a count budget and a Base64 payload budget.
2. It replaces every older image with one line that names the file, in the position the image held.
3. It gives a `compaction` and a `title` request a **zero** image budget, so the recovery path always
   works.
4. It learns a cap it did not know. On `Too many images in request: 69 > 30` it stores `30` for that
   provider and model, then asks for one immediate retry. The retry rebuilds the request with the
   smaller budget and passes.

A pruned image reads:

```
[image omitted from this request by the image budget: /tmp/opencode/kvm/anji4.jpg (image/jpeg, 90 KiB). Read the file again to look at it.]
```

The model can re-read the path when it needs the pixels again, and the stored history keeps every
image, so nothing is lost.

## Options

`kdn.opencode.imageBudget` in the `opencode` aspect:

| Option | Default | Meaning |
| --- | --- | --- |
| `maxImages` | `8` | How many images one request may carry. |
| `maxBytes` | `"8MiB"` | The cumulative Base64 payload of those images. |
| `compaction.maxImages` | `0` | How many images a compaction or title request may carry. |
| `compaction.maxBytes` | `0` | The payload of those requests. |
| `providers.<id>` | `{}` | Per-provider `maxImages` / `maxBytes`. |
| `models."<provider>/<model>"` | `{}` | Per-model `maxImages` / `maxBytes`. |
| `debug` | `false` | Log one line per pruned request to the server log. |

```nix
kdn.opencode.imageBudget.providers.litellm = {
  maxImages = 32;
  maxBytes = "32MiB";
};
```

## Local models

A local llama.cpp server has no image-count cap, so `maxImages` there is a **cost** decision, not a
safety one: every image costs roughly 1k tokens of the context window, and a local model has a small
window. The default of 8 works for a 32k window. Raise `providers.<id>.maxImages` only when a
workflow needs more than eight images at once, and keep an eye on `maxBytes`.

## Recovering a session that is already over the cap

The plugin handles it on the next request: open the session and send a message. No repair step is
needed. If you would rather shrink the history itself, `/compact` now works too, because a compaction
request carries no images.

## What it does not do

- It does not resize or transcode an image. `media.image.max_width`, `max_height` and
  `max_base64_bytes` in `opencode.jsonc` do that, and they apply to the `read` tool as well.
- It does not delete images from the database. The prune is outgoing context only.
- It cannot help a `generate` request that fails on image count before the first retry: a transient
  generation has no retry path in OpenCode 2.2.5. The `generate` hook still prunes, so only a
  first-contact failure with an unknown cap is exposed, and the learned cap covers every request
  after it.
