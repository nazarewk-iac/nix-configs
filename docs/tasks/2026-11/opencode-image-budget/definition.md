# OpenCode image budget

## Context

Session `ses_e08537bd0ffefJDF6MXtcOmSVO` ("Anji SSH lockout after SSHD swap") became unusable. Every
request failed with:

```
AI.Error: Too many images in request: 69 > 30
```

The session had collected 69 `image/jpeg` parts while driving a NanoKVM through screenshot loops.
The images live in `session_message.data` at `content[].state.content[]` as
`{ type: "file", uri: "data:image/jpeg;base64,…", mime, name }` items inside `read` tool results.

## Root cause

Three facts combine:

1. **The cap is the gateway's, not OpenCode's.** requesty and the OpenCode gateway cap a request at
   30 images; Azure caps at 50. The limit is not in the model metadata (`Model.Info` has no image
   count) and there is no configuration for it.
2. **OpenCode has no client-side image-count guard.** It caps image *bytes*
   (`media.image.max_base64_bytes`, 5 MiB by default) and never the count. So 69 small screenshots
   of ~90 KB each pass every client check and are rejected by the gateway.
3. **An image-count rejection is not context overflow.** `compaction.auto` recovers from a
   "too long" rejection only. An image-count 400 is classified `provider.invalid-request` and
   retried unchanged, so it fails again. `/compact` fails the same way, because a compaction
   request carries the same images. The session has no self-recovery path left.

Upstream tracks this in #47487, #47721, #48095, #48781, #51073 and #55060; PR #59303 (open) makes
an image-count error compact with the images removed. Nothing is released.

## Decision

Write a plugin, not a config change: no configuration field can cap the count.

`kdn.image-budget` is an OpenCode V2 server plugin, generated by the `kdn.opencode` den aspect:

- **Prune the request, not the transcript.** The `context` hook runs after OpenCode assembles the
  request and before the provider sees it. Keep the newest images inside a count budget and a byte
  budget; replace every older image with one line that names the file. The stored transcript keeps
  every image, so nothing is lost and the next request prunes again.
- **Zero images for `compaction` and `title`.** A summary does not need pixels, and a compaction that
  still carries 69 images fails exactly like the request it was meant to rescue. This is the piece
  that makes the official recovery path work again.
- **Learn an unknown cap.** The `retry` hook runs after OpenCode classifies a failure and before it
  schedules a retry. The plugin parses `Too many images in request: 69 > 30` (and the Azure and
  upstream wordings), stores the cap per provider and model, and asks for one immediate retry. The
  retry rebuilds the request, so the new budget applies. The learned value survives a restart in the
  plugin storage.

Defaults: 8 images and 8 MiB of Base64 payload, which is below every known cap and costs about 8k
tokens of context. A local llama.cpp server has no count cap, so there the numbers are a cost
decision; `kdn.opencode.imageBudget.providers.<id>` raises them per provider.

## Alternatives rejected

- **Integrate `Sugamsss/opencode-prune-images`.** It targets the V1 plugin API and its V2 support is a
  best-effort layer over hooks it does not own; it also caches images to disk, which this workflow
  does not need. The plugin here is about 300 lines, has no dependency, and fits the aspect that
  already generates the other OpenCode plugins.
- **`HoboStank/opencode-image-guard`.** A hard cap with no card and no compaction handling: it drops
  images silently and does not unstick a session that is already over the cap.
- **Database surgery only.** Proven to work (issue #48781) and used as the fallback, but it is a
  one-shot repair. It does not stop the next screenshot loop.

## Verification

- 59 unit checks: the pure functions (`parseSize`, `payloadBytes`, `collect`, `prune`, `parseCap`) plus the hook wiring (registration, the default and the learned budget, the compaction zero budget, the one-shot retry).
- Live, against the bricked session: `POST /api/session/…/generate` returned `{"data":{"text":"ok"}}`
  where it previously returned 503 with the same message.
- Live, on a fork of that session (identical 69-image history): a full agent turn finished with
  `outcome: "succeeded"`.
- Self-healing: with the budget forced to 200 images, the first turn failed at `69 > 30`, the retry
  hook learned `30`, the forced retry pruned to 28, and the turn finished `succeeded`.
- The prune does not persist: the original session still holds 69 images after the requests.

## Notes

- The count check runs in OpenCode's AI layer while it lowers the assembled messages into the
  provider request, so it sees whatever the hook left behind. That is why pruning in the hook works.
- The slot route (`modules/slots/opencode/`) does not carry the plugin. The slot stays the legacy
  route; the den aspect is what this repository and its adopters use.
