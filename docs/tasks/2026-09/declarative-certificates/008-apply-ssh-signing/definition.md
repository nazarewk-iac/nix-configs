# 008 — apply signs SSH leaves

Hub: [../definition.md](../definition.md). Follows
[005-ssh-ca](../005-ssh-ca/definition.md) and
[006-zellij-migration](../006-zellij-migration/definition.md).

## Context

`kdn-certs apply` generates and signs **TLS** leaves only. The generation loop
(`packages/kdn-certs/internal/generate/generate.go`) calls
`smallstep.StepCLI.SignLeaf`. That method refuses an SSH leaf with a clear error
(`packages/kdn-certs/internal/smallstep/smallstep.go:131-134`):

```go
if req.Type == "ssh-user" || req.Type == "ssh-host" {
    return fmt.Errorf("ssh leaf %q: the SSH sign flow is sub-task 005, not the TLS signer", req.CommonName)
}
```

The SSH sign path exists, but it is wired into `kdn-certs ssh login` alone
(`packages/kdn-certs/cmd/ssh.go`). `ssh login` signs a **user** certificate for a client that
connects to a host. It never writes a server file.

The design § 7 says `apply` signs the host certificate: the server presents `HostCertificate`. So
a declared `ssh-host` leaf is not generated by `apply` today. This is the gap that
[005-ssh-ca/done.md](../005-ssh-ca/done.md) records as a follow-up.

## Goal

`kdn-certs apply` generates and signs every declared leaf, whatever its `type`. A `tls-server` or
`tls-client` leaf keeps the current `step` path. An `ssh-user` or `ssh-host` leaf uses the
OpenSSH-native `ssh-keygen -s` path that `ssh login` already uses. `apply` then writes the public
SSH certificate and SOPS-encrypts the private key, exactly as it does for a TLS leaf.

## What must change

1. **The generation loop branches on `type`.** `internal/generate/generate.go` sends an SSH leaf to
   the SSH signer and a TLS leaf to the TLS signer. The branch sits in `generateOne`, next to the
   existing `keySource` switch.

2. **The SSH key is an ed25519 key, not an EC P-256 key.** The TLS path calls
   `Signer.GenerateKey` (`step crypto keypair --kty EC --curve P-256`). The SSH path needs
   `SSHSigner.GenerateSSHKey` (`ssh-keygen -t ed25519`), which also writes the public key at
   `<keyOut>.pub`. The TLS path has no public key file; the SSH sign reads one.

3. **The SSH sign request is built from the leaf.** `smallstep.SSHCertRequest` needs:
   - `KeyID` — for example `<commonName>`.
   - `Principals` — the leaf `principals`.
   - `Validity` — a per-class lifetime. The interactive class is short (hours); the automation
     class is longer (days). The design § 7.0 allows one lifetime per class. The exact values are a
     security choice and stay with the task owner.
   - `Host` — `true` for `ssh-host`, `false` for `ssh-user`.
   - `PubKeyPath` — the generated `<keyOut>.pub`.
   - `CAKeyPath` — the decrypted SSH CA key.

4. **The CA must sign SSH.** The leaf's `ca` must name a `kdn.ca-dag.cas.<name>` node with
   `ssh = true`. A leaf that names a non-SSH CA is a hard error, exactly as `ssh login` reports it
   (`packages/kdn-certs/cmd/ssh.go:83-85`).

5. **The public certificate path.** `ssh-keygen -s` writes `<pub without .pub>-cert.pub`. The leaf
   declares `certFile` and `keyFile` under `directory`. The loop writes the SSH certificate to
   `<directory>/<certFile>` and the SOPS key to `<directory>/<keyFile>.sops`, so the storage rule of
   design § 4.1 holds. The loop must move the `ssh-keygen` output to `<certFile>` when the two names
   differ.

6. **The test CA path.** `internal/generate/generate_test.go` drives the real loop against a
   temporary unattended CA. It gains an SSH leaf case: a declared `ssh-host` leaf, a CA with
   `ssh = true`, and an assertion that the resulting certificate is a host certificate and verifies
   under the CA. `internal/smallstep/smallstep_test.go` already signs real SSH user and host
   certificates against a test CA, so the signer itself is covered.

## Acceptance test

1. `kdn-certs apply --dry-run --json` lists an `ssh-host` leaf with a reason instead of an error.
2. `kdn-certs apply` against a test CA (the `kdn-certs-test-ca` check) writes the SSH host
   certificate and the SOPS key, and a second run is idempotent.
3. `ssh-keygen -L -f <certFile>` reports a host certificate for `ssh-host` and a user certificate
   for `ssh-user`.
4. The generated certificate verifies under the declared SSH CA.
5. The existing TLS cases keep passing: `kdn-certs-test` and `kdn-certs-test-ca` exit 0.

## Out of scope

- No change to the leaf option shape. No new option.
- No change to the SSH CA, its recipients, the certificate lifetimes or the SSH principals.
- No change to `kdn-certs ssh login`; it stays the interactive client path.
- No change to `.sops.yaml`, `data/ca/`, or a host's certificate files.
- No migration of any host to the den route.

## Follow-up notes

The SSH sign path reads the CA key directly with `ssh-keygen -s`, so it needs no `ca.json` and no
provisioner. That is the path `ssh login` already proves. The work here is the branch in the
generation loop and the ed25519 key, not a new signer.
