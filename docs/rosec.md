# rosec Secret Service

`rosec` is the Secret Service daemon (`org.freedesktop.secrets`) this tree uses. It runs as a
user service and stores secrets in the **`rosec-sops` provider**: a sops-encrypted file tree
under `~/Nextcloud/drag0nius@nc.nazarewk.pw/important/rosec-storage/`. The provider values are
user-level, so they live in one Home Manager module, [`data/rosec.nix`](../data/rosec.nix),
imported by both the universal tree (oams) and the den tree (brys); the two render the same
`config.toml`.

The daemon comes from the **`nazarewk-iac/rosec` fork** (`github:nazarewk-iac/rosec`), which adds
the native provider. The fork's own maintenance guide is `docs/MAINTAINING.md` in that
repository.

The oams store is **derived**: every item file is encrypted to a derived sops identity, and that
identity is stored once as a sops-encrypted master file wrapped to the **oams and brys unattended
YubiKeys**. One unlock per session; item reads and writes then cost no YubiKey operation.

## The unit: upstream or custom

The rosec package ships `share/systemd/user/rosecd.service`: `Type=dbus`,
`BusName=org.freedesktop.secrets`, `ExecStart=…/rosecd`, `WantedBy=default.target`,
`Also=rosecd.socket`, plus rosec's own hardening notes (`LimitMEMLOCK=infinity`, `PrivateNetwork=no`,
and the list of directives that must not be used because they would hide the FUSE mount or imply
`NoNewPrivileges`).

The kdn modules originally defined their own unit instead of using that file, for four reasons the
upstream unit does not cover:

1. the daemon shells out to `sops` and `age-plugin-yubikey` (and now `age-plugin-tpm`), which are
   not guaranteed to be on a login `PATH`, so the module sets an explicit `PATH`;
2. `SOPS_AGE_KEY_FILE` must point at the per-user key file;
3. `rosec-keys.service` (the YubiKey identity merge) must run before the daemon,
   via `Wants`/`After`;
4. the Sway desktop used a name-holder unit (`kdn-secret-service`) and the module supplied the
   process under that name, with `rosecd.service` as an alias.

Measured on 2026-11-18, the two hosts run **different** units: oams runs the custom
`kdn-secret-service.service`; brys runs the upstream `rosecd.service` that the **package** ships
(`share/systemd/user/rosecd.service`, found through the user profile's `share/systemd/user`, and
D-Bus-activated by the package's `org.freedesktop.secrets.service` file).

brys now keeps that unit and adds a **drop-in**, `~/.config/systemd/user/rosecd.service.d/10-kdn.conf`
(`PATH`, `SOPS_AGE_KEY_FILE`, `Wants`/`After=rosec-keys`), plus the alias
`kdn-secret-service.service -> rosecd.service` (a relative symlink, the systemd alias form). The
desktop name-holder is not a second unit any more. `rosec-keys.service`, `rosec-unlock.service`
and `rosec-conflicts` stay as our additions.

oams still defines the custom unit; the same drop-in + alias shape is the pending change there
(the NixOS default `overrideStrategy = "asDropinIfExists"` makes `systemd.packages` plus a partial
`systemd.user.services.rosecd` definition a drop-in, so the shape ports directly).

## Store modes (fixed at creation)

Two modes exist:

- **`direct`** — item files are encrypted to the unlock keys themselves (the YubiKeys). This is the
  original behaviour: one YubiKey operation per decrypt.
- **`derived`** — item files are encrypted to a derived sops identity; that identity is stored as a
  sops-encrypted master file whose recipients are the unlock group. One unwrap per session.

The mode is recorded in plaintext at `<store>/.rosec-store.yaml`:

```yaml
version: 1
mode: derived
```

**There is no default.** A store without this file, or with a missing/unknown mode, is refused: a
guess would encrypt new items to the wrong recipients. The mode never changes in place. The only
supported change is a new store plus a migration:

```sh
rosec-sops store init --mode direct|derived --store <path>
rosec-sops store migrate --from <src> --to <dst> [--mode direct|derived] [--force]
rosec-sops store show --store <path>
```

The oams store is `derived`. Its previous `direct` store is kept at
`~/.local/state/rosec/direct-backup-20261114` (one `_meta.sops.yaml`); delete it once satisfied.

## Unlock once (derived mode)

The store root holds these files:

- `<store>/.rosec-store-identity.sops.yaml` — the **master**: a sops file with one `identity` field,
  encrypted to the unlock group.
- `<store>/.rosec-store-identity.recipient` — the derived **public** recipient (no secret).
- `<store>/.sops.yaml` — two creation rules; the master rule **must be first**, because sops uses
  the first matching rule:

```yaml
creation_rules:
  # The unlock group: any one recipient unwraps the master once per session.
  - path_regex: '^\.rosec-store-identity\.sops\.yaml$'
    age: >-
      age1yubikey1q25g9xpunct74wnn29dgcgep78q666dkhpfg2flltg92fvyrew02j28464d,
      age1yubikey1q0ke6fjulkqg0x0elweecppfkqqr6cqsr42u8q5k5z6466mu60gjseq6p4t
  # Every item: the derived identity only.
  - path_regex: '\.sops\.yaml$'
    age: age1v4y8577rs8374lu4lfw7sgpq9mu8acd0q0zel4aygtfsvcj7zy3sdmy6e9
```

The first recipient is the oams unattended YubiKey, the second the brys one. The master rule may
use any sops key group (`age:`, `pgp:`, `kms:`, `hc_vault:`), so other modes work for the unlock
group; the item rule uses the derived age recipient.

Unlock flow:

1. `sops -d --extract '["identity"]' .rosec-store-identity.sops.yaml` with the local key file. This
   is the **only** YubiKey operation of the session.
2. The derived identity is written to `$XDG_RUNTIME_DIR/rosec/store-identity.age` (mode 0600).
3. Every item read/write uses that runtime identity: **zero** YubiKey operations.
4. `lock` (or a daemon shutdown) removes the runtime file.

The key file is generated by `rosec-keys.service`, which runs the same
`age-plugin-yubikey` generator as the sops-nix setup, filtered to slot 3, and merges the identities
into `~/.config/sops/age/rosec-keys.txt` with `sort -u` — the sops-nix pre-start pattern, but as a
user service and a user-owned file.

The service runs at login, and `rosec-keys.path` triggers it whenever a USB device node appears or
disappears (`PathChanged=/dev/bus/usb`; the YubiKey is one of those devices). Plugging a different
key runs the merge; unplugging runs it too, but only the identity already in the file is kept. The
merge is additive, so the identity of a key you unplugged stays and the other key still unwraps the
master. You can always force a run:

```sh
systemctl --user start rosec-keys
```

The service runs `age-plugin-yubikey --identity --slot 3`. To unlock with the **brys YubiKey on
oams**, plug it in; the path unit (or the manual start) adds its slot-3 line, and the master
already lists the brys recipient. The full `keys.txt` is left alone: it carries slots 1, 2 and 3,
and each identity costs one plugin process.

The service is enabled but not started by a switch (`systemd.user.startServices = "suggest"`);
start it once, or log out and in. Manual fallback for debugging only:

```sh
age-plugin-yubikey -i --slot 3 | grep '^AGE-PLUGIN-YUBIKEY' > ~/.config/sops/age/rosec-keys.txt
chmod 600 ~/.config/sops/age/rosec-keys.txt
```

Prove the split:

```sh
SOPS_AGE_KEY_FILE=~/.config/sops/age/rosec-keys.txt strace -f -e execve -o /tmp/u.strace \
  sops -d --extract '["identity"]' <store>/.rosec-store-identity.sops.yaml >/dev/null
grep -c age-plugin-yubikey /tmp/u.strace   # 1

SOPS_AGE_KEY_FILE=/run/user/$(id -u)/rosec/store-identity.age strace -f -e execve -o /tmp/i.strace \
  sops -d <store>/default/_meta.sops.yaml >/dev/null
grep -c age-plugin-yubikey /tmp/i.strace   # 0
```

The runtime identity is a session-lifetime secret on tmpfs. `lock` removes it; a daemon crash
leaves it until logout, and the next start reuses it without another unwrap. That is the deliberate
trade for "one activation per session".

## Identity operations

```sh
rosec-sops identity init --store <store>      # new derived store: master + sidecar
rosec-sops identity show --store <store>      # recipient, master, runtime state
rosec-sops identity rewrap --store <store>    # re-wrap the master to the current .sops.yaml rule
rosec-sops identity rekey --store <store>     # new derived identity + re-encrypt every item
rosec-sops identity migrate --store <store>   # derived store whose items are still direct
```

**Add an unlock key**: add its recipient to the master rule, then run `identity rewrap`. **Remove
one**: remove the recipient, then rewrap. The removed key may have cached the master, so true
revocation needs `identity rekey`, which rotates the derived identity and re-encrypts the whole
store. Add the new key **before** removing the old one, and never remove the last key you can use:
`sops updatekeys` cannot decrypt the master without a remaining old key.

`identity init` refuses a store that already has items or a non-`derived` mode. `identity
rekey`/`rewrap`/`migrate` preserve the mode. A mode change is `store migrate` into a new store.

## Options

The universal module declares `kdn.services.rosec`:

- `enable` — run `rosecd`. **Off on `oams` until the KeePassXC migration**, because KeePassXC holds
  the bus name (two units cannot own `org.freedesktop.secrets`; the second one is killed).
- `package` — defaults to the fork's flake output.
- `extraPackages` — extra binaries on the unit `PATH`.
- `providers.sops.path` — the store root.
- `providers.sops.key_file` — the local unlock identity; in `derived` mode it only unwraps the
  master. On oams it is the slot-3-only `rosec-keys.txt`.
- `providers.sops.identity_file` — the master file. Empty means `direct` mode; non-empty means
  `derived` and must match the store metadata.
- `providers.sops.identity_key_file` — the key for the master unwrap; empty reuses `key_file`.
- `providers.sops.runtime_identity_file` — where the unwrapped identity lives; empty uses the
  provider default under `$XDG_RUNTIME_DIR`.
- `providers.sops.keyGeneration.{enable,slot,keyFile,scripts}` — generate the key file from the
  YubiKey at login. `slot` defaults to 3 (the `yk-*-unattended` keys); `keyFile` defaults to
  `key_file`; `scripts` defaults to the slot-3 `age-plugin-yubikey` generator and may include the
  merged `kdn.security.secrets.age.genScripts` for extra sources.
- `providers.sops.age_recipient` — the recipient for new item files: the YubiKey recipient in
  `direct` mode, the derived recipient in `derived` mode.
- `providers.sops.{sops_binary,sopsPackage,agePluginYubikeyPackage,probe_timeout_seconds}`.
- `ssh_fuse` — the built-in SSH agent/FUSE tree. Off here; the stock OpenSSH agent serves keys.
- `conflictNotification.{enable,notify,swaync,interval,stateFile}` — independent of `enable`; it
  reads the store, not the daemon.

The den aspect uses `use` instead of `enable` (the aspect rules forbid a reachable `enable`) and
targets `homeManager` only.

## Update rosec (including the fork)

1. **Update the fork** first. Follow `docs/MAINTAINING.md` in `nazarewk-iac/rosec`: fetch
   upstream, rebase `sops-provider` and `devenv`, re-join `main`, run the tests, push the
   bookmarks. The final `main` commit id is the new rev.
2. **Bump the input** in this repository:

   ```sh
   nix flake update rosec
   git diff flake.lock   # confirm the new rev
   ```

3. **Build and switch** (commit the lock first; the tree is shared with other sessions):

   ```sh
   ./nixos-rebuild.sh switch
   ```

4. **Verify**:

   ```sh
   rosec --version
   rosec-sops store show
   rosec-sops conflicts list
   systemctl --user status rosec-keys.service
   systemctl --user status rosec-keys.path
   systemctl --user status rosec-conflicts.path rosec-conflicts.timer
   ```

   `systemd.user.startServices` is `"suggest"` in this tree, so a switch **enables** a new unit
   but does not start it. Start the conflict units once after the first switch (a logout/login
   does it automatically):

   ```sh
   systemctl --user reset-failed rosec-conflicts.path 2>/dev/null || true
   systemctl --user start rosec-conflicts.path rosec-conflicts.timer
   ```

   An existing store needs one explicit mode before the new provider will unlock it:

   ```sh
   rosec-sops store init --mode direct --store <old-store>   # adopt a legacy direct store
   rosec-sops store init --mode derived --store <new-store>  # then identity init
   ```

   While `enable = false` (before the migration), test the provider against a **private bus**.
   The Secret Service unlock prompt uses `SSH_ASKPASS` when there is no TTY; the sops provider
   ignores the input, so a stub is enough for a headless test:

   ```sh
   mkdir -p /tmp/rosec-test
   printf '#!/bin/sh\necho test-unlock-input\n' >/tmp/rosec-test/askpass
   chmod +x /tmp/rosec-test/askpass
   SSH_ASKPASS=/tmp/rosec-test/askpass rosecd --socket /tmp/rosec-test/bus --no-migrate &
   export DBUS_SESSION_BUS_ADDRESS=unix:path=/tmp/rosec-test/bus
   printf 'secret-value\n' | secret-tool store --label=poc service poc
   secret-tool lookup service poc        # prints secret-value
   secret-tool clear service poc
   ```

   After the migration (`enable = true`), the live session bus serves the same clients.

## Conflict workflow

The provider resolves a conflict by **latest `modified` wins** and never deletes the loser:

- the losing copy is archived as `<id>.superseded-<nanos>-<host>.sops.yaml`;
- a plaintext, secret-free marker is written under `.conflicts/<collection>/<id>.md`;
- the item carries `rosec:sops-unresolved-conflict` until the marker is resolved.

The `rosec-conflicts` script notifies once per new conflict (swaync + desktop notification) and
records it in `~/.local/state/rosec/conflicts.json`. The **timer** is the reliable route: a systemd
path unit watches one directory and is not recursive, so a write inside `<collection>/` does not
trigger it. The path unit stays as a best-effort root-level fast route; the timer rescans every
minute. The notification calls are bounded by `timeout`, so a stuck desktop daemon cannot block the
scan. Resolve with the provider CLI:

```sh
rosec-sops conflicts list
rosec-sops conflicts show <item>
rosec-sops conflicts resolve <item> --keep winner|loser|file
```

The better long-term scheme is the follow-up task:
`docs/tasks/2026-11/rosec-conflict-resolution/definition.md`.

### Conflict runbooks

**A bad archive.** A `.superseded-*` file can be corrupt, or encrypted to a key you no longer have.
`rosec-sops conflicts show <item>` names the winner and the losers. If the canonical winner opens,
`resolve --keep winner` deletes the bad archive. If the canonical is the bad copy and the archive is
the good one, `resolve --keep loser` promotes it. If both are bad, restore the item from the
Nextcloud version history or the backup, then delete the marker. The marker is plaintext, so it
survives a store you cannot decrypt.

**Unbounded `.superseded-*` growth.** Every conflict archives a loser and never deletes it, so an
unresolved conflict costs disk and sync traffic forever. The timer reports every archive; resolve
with `conflicts resolve`, which deletes the loser. An orphan archive without a marker (a crash
between the archive write and the marker write) is listed by `rosec-conflicts --list`; inspect the
canonical, then delete the orphan by hand. A retention policy is a possible follow-up.

## KeePassXC → rosec migration (done on `oams`, 2026-11-16)

The Secret Service holds the machine-stored secrets; the personal vault stays in KeePassXC. On
`oams` the live collection exposed **46 items** (all in the KDBX group `drag0nius/secret-service`),
and they now live in the sops store.

`hack/keepassxc-to-rosec.py` is the copy tool:

- read the live bus (`Item.Attributes`, `secret-tool lookup Uuid=<uuid>`);
- write through a **private** `rosecd --socket` in a `0700` directory, so KeePassXC stays untouched
  until the cutover;
- copy every public attribute **verbatim** (the clients' search contract) and the secret as
  `password`, in `[item]` + top-level `[attributes]`/`[secrets]` TOML;
- verify from the destination through `secret-tool`, then stop the private daemon.

The cutover is one switch:

- `kdn.services.rosec.enable = true` and `kdn.services.rosec.rosecd.enable = false` (the module's
  own unit would be a second `Type=dbus` owner);
- the `kdn-secret-service` name holder runs the `rosecd` instead of `sleep infinity`;
  `nextcloud-client` keeps its `Requires` on the holder;
- `kdn.programs.keepassxc.service.enable = false`, forced in the Home Manager evaluation because the
  module forwards the option with `mkDefault`;
- `[FdoSecrets] Enabled=false` in `keepassxc.ini` and `FDO_ENABLED=false` in `kdn-keepass.sh`, so a
  GUI start cannot reclaim the bus.

Result: `busctl --user status org.freedesktop.secrets` names the `rosecd`, all 46 items read back
through `secret-tool`, `nextcloud-client` is active, and the KDBX is untouched. Delete the
`secret-service` group in KeePassXC when the copy is no longer needed.

## Troubleshooting

- **`the store has no mode`** — run `rosec-sops store init --mode direct|derived --store <path>`.
  There is no default by design.
- **Mode mismatch** — the config's `identity_file` and `<store>/.rosec-store.yaml` disagree. A
  `derived` store needs `identity_file`; a `direct` store forbids it. Fix the config, or migrate
  to a new store.
- **Unlock fails** — the local key cannot open the master: check `rosec-keys.txt`, the YubiKey
  slot, and the master rule recipients. `rosec-sops identity show` prints the paths.
- **The brys YubiKey does not unlock on oams** — plug it in and run
  `systemctl --user start rosec-keys`; the service adds its slot-3 identity. If the file still lacks
  it, check `journalctl --user -u rosec-keys`.
- **`rosec-keys.path` failed with `trigger-limit-hit`** — `/dev` is written every second
  (`/dev/null` and friends), so a `/dev` watch hits the limit; `PathExistsGlob=/dev/hidraw*` is
  level-triggered and re-fires after every run. The current unit watches `PathChanged=/dev/bus/usb`,
  which is quiet until a USB device is plugged or unplugged. `systemctl --user reset-failed
rosec-keys.path` and start it.
- **`rosec-keys.service` failed or the key file is empty** — the YubiKey is not plugged in or
  `pcscd` is not ready. Plug it in and start the service again. The merge keeps the old lines, so a
  previous key still works; the service runs again at the next login.
- **The runtime identity is absent** — expected while locked; the next unlock unwraps the master.
  A daemon crash can leave it until logout; `lock` removes it.
- **`rosec-conflicts.path` failed with `trigger-limit-hit`** — an old unit definition with
  `DirectoryNotEmpty`; `systemctl --user reset-failed rosec-conflicts.path` and start it. The
  current definition has no level-triggered directive.
- **A conflict notification repeats** — the state file keys on the conflict path; delete the
  stale record in `~/.local/state/rosec/conflicts.json` if a file was removed by hand.
- **`config file is readable by group or others`** — the Nix store symlink is mode 444; the file
  holds no secret, so the warning is expected.
